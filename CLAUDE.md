# askaipods — project instructions

A zero-dependency npm CLI (`askaipods`) and companion [agentskills.io](https://agentskills.io) skill that wraps the [podlens.net](https://podlens.net) semantic search API, returning recent quote excerpts from 80+ AI-centred podcasts. Distributed as a global CLI via `npx` / `npm install` and as a skill drop-in under each runtime's `skills/` directory (`~/.claude/skills/`, `~/.agents/skills/` for Codex and OpenClaw, `~/.openclaw/skills/`, `~/.hermes/skills/`). README holds the authoritative per-runtime path table.

## Release notes style

GitHub release notes describe **what changed**, not **how the change was arrived at**. Do not mention Codex quality review rounds (R1, R2, ...), `plugin-dev:skill-reviewer` passes, `/verify` scans, `/code-audit` iterations, model identifiers, rejected-finding references, round counts, or "quality gates passed" sections. Include: features, fixes, contract changes, user-facing string changes, breaking changes, honest limitations, migration notes, and deferred scope for the next release (named in plain English, without review artifacts).

Release notes are written for npm / GitHub consumers, not for internal project history. The `v0.2.3` and `v0.2.4` release notes are the cleanest style templates.

This rule applies to the GitHub release body only — not to git commit messages (where referencing the review process for internal repo history is fine) and not to internal review transcripts.

## Release workflow

Run this workflow only when the user asks for a release; that request covers steps 3-4 and 7, step 5 stays the user's, and step 6 is prepared here and committed on the user's go-ahead.

1. **Bump the version in four locations** (all four must match, every time; `npm test` enforces it):
   - `package.json` `"version"`
   - `skill/askaipods/scripts/cli.mjs` `const VERSION = "..."`
   - `skill/askaipods/scripts/client.mjs` `User-Agent` header string
   - `skill/askaipods/SKILL.md` pinned fallback `npx -y askaipods@X.Y.Z`
2. **Recapture the README hero** (the sample output at the top of README.md) in the same commit, so episode titles and results do not drift. Re-run its command with `--format markdown` added (stdout that is not a terminal defaults to JSON, and each run is a charged search) and replace the block with the new real output — never hand-edit titles, dates or quotes; soft-wrapping quote lines is the only allowed change. Prefer an anonymous capture (no key, no `--days`) so the header reads `Tier: anonymous`; when the IP's anonymous quota is used up, capture with a key plus `--days 30` and keep the command line and the italic note under the block saying so. Update the capture date in that note. If the top results have gone off-topic, pick a new query rather than trimming the list.
3. **Commit and push to `main`.** The `.github/workflows/auto-tag.yml` workflow runs on every push to `main` that touches `package.json`; when no `vX.Y.Z` tag exists for the version in `package.json`, it creates and pushes one, and when no release exists for that tag, it publishes a placeholder GitHub release (title = tag, auto-generated notes) so the "Latest" release never lags the newest tag. It looks at what exists on the remote, not at the previous commit, so a version bump anywhere in a multi-commit push gets its tag; the tag points at the last commit of that push. When that run fails its tests and the fix does not touch `package.json`, no push starts the workflow again: once the fix is on `main`, start it by hand with `gh workflow run auto-tag.yml --ref main`.
4. **Replace the placeholder release notes** with `gh release edit vX.Y.Z --title "vX.Y.Z — <short descriptor>" --notes "$(cat <<'EOF' ... EOF)"`, following the §Release notes style rule above. If the workflow failed to create the release, use `gh release create` with the same arguments instead. Do not delete-and-recreate (URLs break, subscribers re-notified).
5. **Publish to npm** (`npm publish`) right after the push if the release is a source change — skip npm publish for release-note-only corrections. Do not leave a gap: SKILL.md's fallback pins `askaipods@X.Y.Z`, which fails for anyone pulling `main` until that version is on npm. Authenticate interactively (`npm login --auth-type=web`) and complete the 2FA prompt on publish; do not store a long-lived publish token in `~/.npmrc` — npm is removing direct-publish rights from 2FA-bypass granular tokens (January 2027). The 2FA step needs the user, so Claude hands this command to the user rather than running it.
6. **Bump the discovery pin on podlens.net** in the same sitting, once the tag from step 3 exists. `~/Desktop/podlens-site/.well-known/agent-skills/index.json` pins this skill to a tag URL and the `sha256` of that tag's `skill/askaipods/SKILL.md`; nothing updates it, so every release leaves the site advertising the previous version until someone edits it (the v0.3.5 and v0.3.6 releases both left it one version behind). Follow podlens-site `docs/claude/seo-and-agents.md` §Bumping askaipods version: new tag in `url`, new `digest` (`git fetch origin tag vX.Y.Z && git show vX.Y.Z:skill/askaipods/SKILL.md | shasum -a 256`), the example literal in that section, and `llms-full.txt` only when `toStructured`'s result keys changed. It is a commit in another repository: prepare the edit, then ask before committing and pushing it there.
7. **Run the live smoke test** once the version from step 5 is on npm (`npm view askaipods version`): `node scripts/live-smoke.mjs`. It runs the published package through `npx` from an empty directory and checks six searches against the live server — without a key and, when `ASKAIPODS_API_KEY` is set, with it, each as default / `--days 1` / `--sort relevance`; its last line says how many of the six were checked and how many skipped, and a release check wants all six. Every run spends real quota (three anonymous searches from the IP's 20/day, three on the key), so run it once, not in a loop: `--out <new dir>` saves the outputs (a directory that already holds saved outputs is refused) and `--replay <dir>` re-checks them without the network. A `FAIL` is a contract fact (tier cap, default window, served ordering, field shapes): the release is not done until it is explained — find out whether the CLI or the server moved. A `WARN` depends on the corpus (fewer than 20 matches, a widened window, an ingest lag, results trailing the newest episode): report it; it does not fail the release. When a contract changes on purpose, change `checkScenario` in the same commit as the code — `tests/live-smoke.test.mjs` covers its rules offline. The same script checks a podlens-site deploy that changes `/api/search/semantic`: run it as is for the published CLI, or with `--local` when the matching CLI change is not released yet.

## Zero-dependency constraint

`package.json` declares no `dependencies` or `devDependencies`, and should stay that way. This is a load-bearing design choice — no third-party code in the supply chain of a CLI that agents run, and a CLI simple enough to ship inside the skill folder (`skill/askaipods/scripts/`), so agents run it with `node` and fetch nothing from npm at search time. The npm package and the publishing account remain supply-chain surface: SKILL.md's `npx` fallback is pinned to an exact version for that reason.

- The CLI source lives in `skill/askaipods/scripts/` as `.mjs` files so it stays ESM when the skill folder is copied out of the package; `bin/askaipods.js` only imports it. Keep one copy of the source.

- Tests must use `node:test` + `node:assert/strict` from the Node standard library. Do not add `jest`, `mocha`, `vitest`, or any other test framework.
- Runtime must stay on Node 18.3.0+ built-ins: `fetch`, `AbortSignal.timeout`, `parseArgs` from `node:util`, `Headers`, `URL`, etc. Do not add `node-fetch`, `commander`, `yargs`, or similar.
- If a truly unavoidable dependency comes up, it's a design discussion, not a mechanical addition.
